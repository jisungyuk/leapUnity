# TS–Go 타이밍 오차 — 원인, 측정 결과, 남은 문제

작성: 2026-10-23 · 대상: RWR 게임 모드 (`TrialGameController_RWR.cs`)

## 요약

- TS↔CS 간격은 PowerLab FRO 하드웨어가 만들기 때문에 정확하다.
- **TS↔Go 간격은 컴퓨터 쪽 오차가 들어간다.** ts=0으로 설정해도 TMS가 정확히 Go 순간에 들어가지 않는다.
- 2026-10-23 변경 후, Unity 기준으로 **TS는 항상 Go보다 먼저** 나가며, 120 fps에서 **평균 −4.8 ± 3.9 ms** (n=20)였다.
- 참가자가 실제로 Go를 **보는** 순간 기준으로는 TMS가 이보다 **더 일찍** 들어간다 (렌더링 + 모니터 지연). 이 값은 아직 측정하지 못했다 (포토다이오드 없음).

## 신호 흐름

```
[Unity] 트리거 결정 ──USB──▶ TriggerBox ──▶ PowerLab ──(500+ts ms, 하드웨어)──▶ TS ──(cs, 하드웨어)──▶ CS
[Unity] Go 결정 ──▶ 프레임 렌더링 ──▶ 모니터 표시 ──▶ 참가자가 Go를 봄
```

- 트리거는 예정 Go 500 ms 전에 나간다 (`TtlLeadS = 0.5f`, 고정값).
- PowerLab FRO가 트리거 기준 `500 + ts` ms에 TS, `500 + ts + cs` ms에 CS를 낸다. 이 구간은 하드웨어 클럭이라 사실상 오차가 없다.

## 오차의 원인

Unity는 매 프레임마다 "예정 시각이 지났나?"를 확인한다. 그래서 트리거와 Go 모두 예정보다 **0~1프레임 늦게** 실행된다 (60 fps: 0~16.7 ms, 120 fps: 0~8.3 ms).

### 이전 방식 (2026-10-23 전)

트리거와 Go가 각자 예정 시각을 따로 확인했다.
- TS−Go 오차 = (트리거 지연 e1) − (Go 지연 e2) → **±1프레임, 방향 불명**

### 현재 방식 (2026-10-23 변경)

트리거가 나간 뒤에는 Go를 **실제 트리거 시각 + 500 ms**에 맞춘다 (`Update_ShowDirection()`).
- 트리거가 늦으면 Go도 같이 늦춰지므로 e1이 사라진다.
- TS−Go 오차 = −e2 → **0 ~ −1프레임, TS가 항상 Go와 같거나 먼저**
- 오차 폭이 절반으로 줄고 방향이 일정해진다.
- 대가: 지시 신호→Go 간격이 최대 1프레임 더 길어진다 (2~3초 대기에 비하면 무시 가능, 실제 값은 헤더 `ready_ms`/`go_ms`에 기록됨).
- LabChart 없이 진행하는 세션(SHIFT+SPACE)은 트리거가 없으므로 예정 시각에 Go.

## 측정 결과 (Unity 프레임 시계 기준)

조건: ts=0, SinglePulse, TriggerBox COM3, Unity 에디터에서 실행, 참가자 폴더 `expdata/MH01/`.

| | session_007 (120 fps) | session_008 (60 fps) | 이론값 (120 / 60) |
|---|---|---|---|
| n | 20 | 20 | |
| 평균 | **−4.8 ms** | **−8.3 ms** | −4.2 / −8.3 |
| 표준편차 | **3.9 ms** | **7.7 ms** | 2.4 / 4.8 |
| 범위 | −13.2 ~ −0.2 | −19.9 ~ −0.1 | 0~−8.3 / 0~−16.7 |
| 한 프레임 초과 | 4개 | 3개 | |

- 40개 모두 TS가 Go보다 먼저 나갔다.
- 평균은 이론값과 일치한다. 120 fps가 60 fps보다 평균·변동 모두 약 절반이다.
- 한 프레임을 넘은 값은 에디터에서 프레임 시간이 순간적으로 길어진 경우로 보인다. 빌드 실행 파일에서는 줄어들 가능성이 높다 (미확인).
- **60 fps 값이 두 무리로 나뉜다** (≈0 또는 ≈−16.7). 500 ms가 정확히 30프레임(120 fps면 60프레임)이라 "트리거 + 500 ms"가 거의 항상 프레임 경계와 겹치기 때문이다. 프레임 시간이 미세하게 흔들리면 그 프레임에 걸리거나(≈0) 한 프레임을 통째로 놓친다(≈−1프레임).

## 참가자 기준 실제 간격 (미측정)

위 값은 "Unity가 Go를 결정한 순간" 기준이다. 참가자가 Go를 **보는** 순간까지는 지연이 더 있다.

| 구간 | 크기 | TMS–Go 간격에 미치는 영향 |
|---|---|---|
| Unity 프레임 오차 (측정값) | 평균 4.8 ms (120 fps) | TMS가 먼저 |
| USB → TriggerBox 지연 | 약 1 ms (추정) | TMS가 조금 늦어짐 → 간격 줄어듦 |
| 렌더링 → 화면 전송 | 0 ~ 1프레임 | Go가 늦게 보임 → 간격 늘어남 |
| 모니터/TV 입력 지연 | 게이밍 모니터 수 ms, TV 20~50 ms 이상 | Go가 늦게 보임 → 간격 늘어남 (**가장 큰 미지수**) |
| 소리 Go 신호 | Windows 오디오 지연 수십 ms | 소리 기준이면 간격 크게 늘어남 |

→ 참가자 기준으로 TMS는 **Go가 보이기 대략 10 ms 이상 전**에 들어갈 가능성이 높다. TV라면 수십 ms 전일 수 있다.

## 앞으로 할 수 있는 것

1. **Unity fps를 120으로 운영** — 게임 설정 패널의 주사율 값. VSync가 꺼져 있어 60 Hz 화면에서도 Unity 쪽 오차는 줄어든다 (화면 표시 지연은 그대로). 120 Hz 모니터면 화면 쪽도 줄어든다.
2. **TV라면 "게임 모드" 켜기** — 입력 지연이 크게 줄어든다.
3. **실제 화면 기준 측정 (포토다이오드)** — 현재 장비 없음. 화면 구석에 Go와 함께 켜지는 흰 사각형 + 포토다이오드 → PowerLab 입력. 측정되면 평균 지연만큼 ts로 보정 가능 (예: 15 ms 일찍 들어가면 ts=15). 표준편차는 보정 불가한 실제 지터로 보고.
4. **반 프레임 여유 (미구현)** — Go 판정을 반 프레임 일찍 허용하면 프레임 경계에서 놓치는 경우가 없어져 오차가 0 근처로 모인다 (이론상 ±반 프레임). 대신 TS가 Go보다 최대 반 프레임 늦게 나갈 수 있다.
5. **빌드 실행 파일로 재측정** — 에디터의 프레임 튐이 빠진 값 확인.

## 데이터에서 확인하는 방법

트라이얼 CSV 헤더:

```
# ts_minus_go_ms: -4.8    ← TS − Go (ms), 양수 = Go 뒤. Unity 프레임 시계 기준
# cs_minus_go_ms:         ← CS − Go, SinglePulse면 빈칸
# ttl_port: COM3          ← 펄스가 실제로 나간 포트, 안 나갔으면 none
# jitter_from_scheduled_ms: -4.8   ← TS−Go에서 설계값(ts)을 뺀 순수 지터
```

- 포트가 열리지 않았으면 시각 값은 빈칸이다. 2026-10-23 이전에는 포트가 없어도 값이 찍혔으므로 (`COM5` 하드코딩 문제), 그 이전 데이터는 `ttl_port`가 없으면 TMS 타이밍 근거로 쓰지 말 것.
